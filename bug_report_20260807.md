# Bug: `migrate consolidate` (Postgres) writes an unappliable file, silently drops schema features, and leaves the source database unable to migrate

**Date:** 2026-08-07
**Version:** joka 0.12.0 (`ff9e1f6`)
**Driver tested:** PostgreSQL 16.14. **MySQL was not tested** — see [Scope](#scope).
**Profile in use:** `local` (`connection.source: env`, Postgres 16 on localhost:40100)

## Summary

`joka migrate consolidate` is destructive before it is correct. It deletes the source migration files,
then leaves behind:

1. a generated file that **cannot be applied** — the first `CREATE TABLE` that owns an index fails with
   `syntax error at or near "CREATE"`;
2. a schema that, once the syntax is hand-repaired, is **silently wrong** — every identity column has
   lost its identity, so the rebuilt database rejects every insert that omits `id`;
3. a source database whose **migration chain is broken**, so every subsequent `joka` command fails,
   including at application boot.

Eight distinct defects are recorded below, each reproduced. Seven are in the Postgres snapshot
reconstruction; one is in the consolidate command itself.

The meta-issue behind all of them: **the command deletes the source files (step 7) before anything
checks that the generated SQL is applicable.** Step 8 "Verify the resulting migration directory looks
correct" (`cmd/migration/consolidate.go:176`) only re-lists filenames. Nothing ever parses or applies
the file it just wrote, so all eight defects surface *after* the inputs are gone.

## Reproduction

Two schemas. The first is a real 31-table application schema; the second is a minimal schema that
exercises the constructs the first happens not to use.

### A. Real schema (31 tables, 30 identity columns)

```bash
# fresh DB, all migrations applied through joka so joka_snapshots is populated
createdb cons_src
export DATABASE_URL="postgres://…@localhost:40100/cons_src?sslmode=disable"
cp -r devops/migrations /tmp/cons
joka init --auto -m /tmp/cons
joka migrate up --auto -m /tmp/cons          # 3 files, 3 snapshots, 31 tables, 30 identity columns

joka migrate consolidate --up-to 260101007100 --auto -m /tmp/cons
```

### B. Minimal fidelity schema (self-contained)

`/tmp/fid/300000000001_fidelity.sql`:

```sql
CREATE TYPE mood AS ENUM ('ok', 'bad');
CREATE TABLE t_serial (id serial PRIMARY KEY, name text);
CREATE TABLE t_ident (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, tags text[], m mood, amt numeric(10,2), created_at timestamptz DEFAULT now());
CREATE INDEX idx_t_ident_tags ON t_ident USING gin (tags);
CREATE TABLE t_child (id int PRIMARY KEY, parent_id bigint REFERENCES t_ident(id));
CREATE TABLE t_check (id int PRIMARY KEY, n int CHECK (n > 0));
CREATE VIEW v_ident AS SELECT id, m FROM t_ident;
CREATE FUNCTION f_noop() RETURNS int AS $$ BEGIN RETURN 1; END; $$ LANGUAGE plpgsql;
```

`/tmp/fid/300000000002_second.sql`: `CREATE TABLE t_second (id int PRIMARY KEY);`
(A second file is needed — `consolidate` refuses with `need at least 2 migrations to consolidate`.)

```bash
joka init --auto -m /tmp/fid && joka migrate up --auto -m /tmp/fid
```

## Group 1 — the output cannot be applied

### 1. `CREATE TABLE` is never terminated when the table owns an index

**Real schema: 27 of 31 tables affected.** Applying the generated file:

```
psql:260101007100_consolidated.sql:16: ERROR:  syntax error at or near "CREATE"
LINE 13: CREATE INDEX idx_key_hash ON public.api_keys USING btree (ke...
```

The output reads:

```sql
CREATE TABLE api_keys (
  ...
)                                    -- no semicolon
CREATE INDEX idx_key_hash ON public.api_keys USING btree (key_hash);
```

**Root cause.** `reconstructCreateTable` builds the table body with no terminator
(`internal/domains/migration/infra/postgres.go:286`):

```go
result := fmt.Sprintf("CREATE TABLE %s (\n%s\n)", tableName, strings.Join(parts, ",\n"))
```

then appends each index **with** one (`postgres.go:312`):

```go
result += fmt.Sprintf("\n%s;", idxDef)
```

So the snapshot value for a table-with-indexes ends in `;`, which satisfies the only terminator check
there is (`internal/domains/migration/app/consolidate.go:116`):

```go
if !strings.HasSuffix(ddl, ";") {
    ddl += ";"
}
```

The check tests the *concatenation*, not each statement. The 4 tables that came out valid are exactly
those with no non-constraint index.

**Fix direction.** Terminate at the source: `…\n);` at `postgres.go:286`. Then
`GenerateConsolidatedSQL`'s suffix check becomes redundant and should be removed rather than left to
paper over a second case.

### 2. Array columns emit the literal word `ARRAY`

`tags text[]` → `tags ARRAY` → `ERROR: syntax error at or near "ARRAY"`.

**Root cause.** The column query selects `data_type` (`postgres.go:211`), and
`information_schema.columns.data_type` is the string `'ARRAY'` for any array column. The element type
lives in `udt_name` (`_text`).

**Fix direction.** Use `format_type(a.atttypid, a.atttypmod)` from `pg_attribute`, which renders
`text[]`, `numeric(10,2)`, `character varying(20)` and user-defined types correctly in one step — and
removes the hand-rolled `charMaxLen` / `numPrecision` / `numScale` assembly at `postgres.go:232-240`.

### 3. Enum / domain / composite columns emit the literal `USER-DEFINED`

`m mood` → `m USER-DEFINED` → `ERROR: syntax error at or near "USER"`. Same root cause and same fix as
defect 2.

### 4. `serial` columns reference a sequence that is never created

`id serial` is captured as `DEFAULT nextval('t_serial_id_seq'::regclass)`, but no `CREATE SEQUENCE` is
emitted anywhere → `ERROR: relation "t_serial_id_seq" does not exist`.

**Root cause.** The snapshot only ever iterates tables (defect 7); sequences are not part of it, while
the *default referencing* the sequence is faithfully copied.

**Fix direction.** Emit owned sequences before the tables that use them, or convert `serial` to the
identity form on capture. `pg_dump` emits `CREATE SEQUENCE` + `ALTER SEQUENCE … OWNED BY`.

## Group 2 — the output applies but the schema is silently wrong

These are the dangerous ones: after hand-repairing the semicolons from defect 1, **the real 31-table
file applies with 0 errors** and produces a schema that is quietly incorrect.

### 5. Identity columns lose their identity

Source: **30** identity columns. Rebuilt from the consolidated file: **0**.

```sql
-- source
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY
-- generated
id bigint NOT NULL,
```

**Root cause.** The column query (`postgres.go:211`) selects
`column_name, data_type, is_nullable, column_default, …` and never `is_identity` /
`identity_generation`. An identity column has **`column_default = NULL`** — identity is not a default —
so nothing is carried across and nothing warns.

**Consequence.** A database rebuilt from a consolidated baseline rejects every `INSERT` that omits
`id`, and it fails at application runtime, long after consolidation "succeeded".

**Fix direction.** Select `is_identity, identity_generation` and emit
`GENERATED {ALWAYS|BY DEFAULT} AS IDENTITY`, or follow `pg_dump` and emit a trailing
`ALTER TABLE … ALTER COLUMN id ADD GENERATED ALWAYS AS IDENTITY (…)`.

### 6. Views are recreated as tables

`CREATE VIEW v_ident` came back as `CREATE TABLE v_ident (id bigint, m USER-DEFINED)`. Had the column
types been valid, this would have **created a real table where a view belonged** — no error, wrong
database.

**Root cause.** The table enumeration has no type filter (`postgres.go:148`):

```sql
FROM information_schema.tables
WHERE table_schema = current_schema()
AND table_name NOT LIKE 'joka\_%' ESCAPE '\'
```

`information_schema.tables` includes views and foreign tables.

**Fix direction.** Add `AND table_type = 'BASE TABLE'`, and capture views separately via
`pg_get_viewdef`.

### 7. Every non-table object is dropped without warning

Confirmed absent from the output: `CREATE TYPE` (enum), `CREATE FUNCTION`, `CREATE SEQUENCE`. By
construction — the snapshot iterates `information_schema.tables` and reconstructs each entry as a
table — this also covers triggers, materialized views, extensions and domains. (Types, functions and
sequences were reproduced; the rest follow from the same enumeration and were not separately tested.)

**Fix direction.** Either capture them, or **refuse to consolidate** when the schema contains an object
class the snapshot cannot represent. A loud refusal is far better than a baseline that is quietly
missing a type. Long term, shelling out to `pg_dump --schema-only --no-owner --no-privileges` is worth
considering: it is the reference implementation for every defect in Groups 1 and 2.

## Group 3 — the source database is left unusable

### 8. Files are deleted but `joka_migrations` is not reconciled

After a successful-looking consolidation of the real schema:

```
files:  260101007100_consolidated.sql          (1)
joka_migrations rows: 260101006900, 260101007000, 260101007100   (3)
```

Every subsequent joka command then fails:

```
$ joka migrate up --auto -m /tmp/cons
Checking migration chain...
Error applying migrations: migration chain broken at index 0: wanted 260101007100 but found 260101006900
```

**Root cause.** `consolidate` rewrites the files but never touches the bookkeeping, and
`internal/domains/migration/app/get_migration_chain.go` zips files against applied rows
**positionally**, so `files[0] != applied[0]` breaks everything.

**Consequence.** Any service that migrates at boot will not start. Recovery requires hand-editing
`joka_migrations`.

**Fix direction.** Reconcile the bookkeeping in the same transaction as the file rewrite — delete the
consolidated-away rows and insert the new index — so the database consolidate ran against remains
usable. This is the one defect that damages an environment rather than just producing a bad file.

## Expected behaviour

`joka migrate consolidate --up-to X` should produce a single migration file that, applied to an empty
database, yields a schema **indistinguishable** from applying the migrations it replaced (verifiable by
diffing `pg_dump --schema-only` of both), and should leave the database it ran against able to migrate.
It should not delete its inputs until it has established the first part.

## Workaround used

jjc2 does not use the command. Its baseline (`260101006900_consolidated.sql`) was produced by hand from
`pg_dump --schema-only --no-owner --no-privileges -T 'joka_*'`, stripping the `SET` / `set_config`
preamble (it sets an empty `search_path`) and the `\restrict` / `\unrestrict` psql meta-commands, then
saved under the index it consolidates up to. Bookkeeping is reconciled by a hand-written
`scripts/db-consolidate-bookkeeping.sql`. Comment lines are kept — they apply fine and are the only
navigation an 1800-line baseline has.

That workaround should be deleted once this is fixed.

## Scope

Everything above was reproduced against **PostgreSQL 16.14 with joka 0.12.0**. Defects 1–7 all live in
`internal/domains/migration/infra/postgres.go` (the `reconstructCreateTable` path). Defect 8 is in
`cmd/migration/consolidate.go` and the shared chain logic, so it is **driver-agnostic**.

MySQL was **not tested**. Reading `internal/domains/migration/infra/mysql.go`, its `ComputeSchema` uses
`SHOW CREATE TABLE`, which returns a complete self-contained statement — so Group 1 and Group 2 probably
do not apply there. That is an inference from source, not a test result; confirm before assuming it.

## Suggested order of work

1. **Defect 8** first — it is the only one that damages a live environment.
2. **Defect 1** — one-line fix, and it unblocks any real use of the command.
3. **Defects 2, 3, 5** together — all one change: replace the hand-assembled column type and flags with
   `format_type()` plus `is_identity`, driven off `pg_attribute`.
4. **Defects 4, 6, 7** — decide the policy: capture non-table objects, or refuse to consolidate a schema
   containing them. Either is acceptable; silently dropping them is not.
5. Add a **post-generation verification** step before deletion: apply the generated file to a scratch
   database and diff `pg_dump` output against the source. That single step would have caught all eight
   of these, and is the thing whose absence let them all ship.
